Diwakar Enterprise CMS — Application Architecture
1. Purpose
This document defines the approved application architecture for Diwakar Enterprise CMS.
The goal is to keep the application:
- understandable
- maintainable
- testable
- secure
- reusable
- aligned with Laravel conventions
- free from unnecessary abstraction
Agents must follow this architecture unless an approved feature explicitly requires a change.
Major architectural changes require user approval.
2. Architectural Principle
Prefer Laravel conventions first.
Do not introduce custom architectural layers merely because they are common in other frameworks or enterprise systems.
Use the simplest structure that cleanly supports the approved requirement.
Avoid:
- speculative abstraction
- unnecessary repositories
- unnecessary interfaces
- premature event systems
- excessive service classes
- generic frameworks built inside Laravel
- over-engineered domain layers without a clear need
3. Primary Application Areas
The application has two primary presentation areas.
Administration
CMS administration interface.
Primary path:
/admin/...
Primary views:
resources/views/admin/
Primary routes:
routes/admin.php
Frontend
Public-facing website.
Primary views:
resources/views/frontend/
Primary routes:
routes/frontend.php
The administration and frontend areas should remain clearly separated.
Shared application logic may be reused where appropriate.
4. Routing Architecture
Frontend routes belong in:
routes/frontend.php
Administrative routes belong in:
routes/admin.php
Laravel route registration is configured in:
bootstrap/app.php
Admin routes use:
URL prefix:
/admin
Route-name prefix:
admin.
Examples:
admin.dashboard
admin.users.index
admin.pages.create
admin.pages.edit
Use named routes for application navigation and redirects.
Avoid hard-coded URLs in Blade views when a named route exists.
5. routes/web.php
routes/web.php is not the primary location for CMS business routes.
The project intentionally separates:
- frontend routes
- admin routes
Do not move routes back into web.php merely for convenience.
If Laravel or an approved package requires a route file integration, evaluate it within the existing routing structure.
6. Controllers
Controllers should remain thin.
A controller should primarily:
- receive the HTTP request
- use validated input
- enforce or invoke authorization
- invoke application logic
- return a response or redirect
Controllers should not contain large amounts of:
- business logic
- database orchestration
- complex validation
- reusable calculations
- file-processing logic
- integration logic
If logic becomes meaningful or reusable, move it to an appropriate Action or Service.
7. Controller Organization
Administrative controllers should normally be grouped under a clear namespace such as:
App\Http\Controllers\Admin
Frontend controllers may be grouped under:
App\Http\Controllers\Frontend
when dedicated controllers are required.
Authentication controllers generated by Laravel Breeze may retain their framework-compatible organization unless an approved refactor changes them.
Do not move files solely for cosmetic consistency if doing so creates unnecessary work.
8. Form Requests
Use Form Request classes for meaningful validation.
Recommended location:
app/Http/Requests/
Administrative requests may be grouped further when useful.
Examples:
app/Http/Requests/Admin/StorePageRequest.php
app/Http/Requests/Admin/UpdatePageRequest.php
Form Requests may contain:
- validation rules
- validation messages where required
- request-level authorization where appropriate
- safe normalization of request input where appropriate
Avoid duplicating the same validation rules across controllers.
9. Validation
All external input must be validated server-side.
Do not rely solely on:
- HTML validation
- JavaScript validation
- Alpine.js validation
Client-side validation may improve user experience, but server-side validation remains authoritative.
Use Laravel validation facilities before introducing custom validation frameworks.
10. Models
Eloquent models represent persisted application data.
Primary location:
app/Models/
Models may define:
- relationships
- casts
- accessors
- mutators
- scopes
- appropriate model-level behavior
Avoid turning models into large service containers.
Complex workflows should be moved into Actions or Services where appropriate.
11. Eloquent Relationships
Define explicit Eloquent relationships where applicable.
Examples may include:
- belongsTo
- hasMany
- belongsToMany
- morph relationships when genuinely required
Use eager loading where needed to avoid N+1 query problems.
Do not eager-load large relationship graphs unnecessarily.
12. Query Logic
Simple query logic may remain close to the model or controller when clear and local.
Reusable query patterns may use:
- model scopes
- dedicated query objects if complexity genuinely requires them
Do not automatically create repository classes for normal Eloquent queries.
13. Repository Pattern
Repository classes are not mandatory.
Do not create a Repository for every model.
Eloquent already provides a persistence abstraction suitable for most CMS functionality.
Use a Repository only when there is a concrete requirement such as:
- multiple persistence backends
- complex reusable persistence behavior
- isolation of a genuinely complicated data-access strategy
- external data-source abstraction
Repository usage requires justification.
Avoid unnecessary interfaces such as:
PageRepositoryInterface
unless they provide real architectural value.
14. Actions
Actions are appropriate for focused application operations.
Recommended location:
app/Actions/
An Action should generally perform one meaningful operation.
Examples:
CreateUser
PublishPage
UploadMedia
UpdateWebsiteSettings
Actions are useful when an operation:
- has meaningful business logic
- involves multiple models
- requires a transaction
- is reused by multiple entry points
- would otherwise make a controller too large
Do not create an Action for every single-line operation.
15. Services
Services are appropriate for cohesive business capabilities that do not naturally belong to a single model or Action.
Recommended location:
app/Services/
Potential examples:
- media processing
- SEO generation
- external integrations
- complex content processing
Services should have a clear responsibility.
Avoid generic classes such as:
CommonService
UtilityService
HelperService
that become dumping grounds for unrelated logic.
16. Actions vs Services
Use an Action when the concept is primarily:
“Perform this application operation.”
Use a Service when the concept is primarily:
“Provide this reusable business capability.”
Do not create both an Action and Service merely to add layers.
Choose the simplest appropriate design.
17. Interfaces
Interfaces should be introduced only when they provide real abstraction value.
Potential valid cases include:
- external provider abstractions
- multiple implementations
- testable integration boundaries
- storage/provider contracts
- architecture requiring interchangeable implementations
Do not create interfaces automatically for every service or class.
Avoid one-interface-per-class boilerplate.
18. Authorization
Authorization must be enforced server-side.
Potential mechanisms include:
- Laravel Policies
- Gates
- approved role/permission middleware
- Spatie Laravel Permission after its feature is approved
Navigation visibility is not authorization.
Hiding a menu option does not prevent unauthorized access.
Sensitive actions must be protected at the request/controller/policy level.
19. Policies
Use Policies where authorization maps naturally to a model/resource.
Recommended location:
app/Policies/
Examples may include:
- view page
- create page
- update page
- delete page
- publish page
Do not duplicate authorization rules in multiple controllers.
20. Middleware
Middleware should be used for concerns that apply across requests.
Potential examples:
- authentication
- role/permission checks
- request-level cross-cutting concerns
Recommended location for custom middleware:
app/Http/Middleware/
Do not place business workflows inside middleware.
21. Blade Views
Views are presentation templates.
Primary areas:
resources/views/admin/
resources/views/frontend/
Avoid embedding substantial business logic in Blade templates.
Blade may contain:
- display conditions
- simple iteration
- formatting-related conditions
- component composition
Complex data preparation should happen before the view is rendered.
22. Blade Components
Use Blade components for reusable interface elements.
Primary component location:
resources/views/components/
Class-based components may use:
app/View/Components/
Examples may include:
- admin layout
- frontend layout
- form field
- alert
- modal
- breadcrumb
- pagination wrapper
- reusable card
Do not create components for trivial one-off markup with no reuse or readability benefit.
23. Layout Architecture
Administrative layout should remain separate from frontend layout.
Current conceptual components include:
<x-admin-layout>
<x-admin-guest-layout>
<x-frontend-layout>
Administrative shared structures may include:
- header
- sidebar
- footer
- breadcrumbs
- notifications
Frontend shared structures may include:
- header
- navigation
- footer
Theme-specific frontend layouts may evolve later through the approved theme architecture.
24. View Partials
Partials may be used for structural fragments that are tightly coupled to a layout.
Examples:
resources/views/admin/layouts/partials/header.blade.php
resources/views/admin/layouts/partials/sidebar.blade.php
resources/views/admin/layouts/partials/footer.blade.php
resources/views/frontend/layouts/partials/header.blade.php
resources/views/frontend/layouts/partials/footer.blade.php
Use a Blade component instead when the element is intended to be independently reusable or configurable.
25. View Data
Controllers or application logic should prepare the data needed by views.
Avoid database queries directly inside Blade templates.
Do not call Eloquent models directly from views to retrieve application data.
Use view composers only when there is a clear shared-data need across multiple views.
26. Database Migrations
All schema changes must use Laravel migrations.
Primary location:
database/migrations/
Migrations should be:
- clear
- minimal
- reversible where practical
- safe for existing data
- appropriately indexed
Do not modify old migrations that may already have been applied merely to change current schema behavior.
Prefer creating a new migration for subsequent schema changes.
27. Migration Safety
Before implementing a migration, consider:
- whether existing rows exist
- whether new fields may safely be non-null
- whether a default is appropriate
- whether indexes are needed
- whether foreign keys may fail on existing data
- whether rollback is safe
Potentially destructive migrations require explicit user approval.
28. Seeders
Seeders may be used for:
- required baseline application data
- development/testing data where clearly separated
- initial roles/permissions if defined by the approved RBAC feature
Primary location:
database/seeders/
Do not place real production credentials or secrets in seeders.
Do not create permanent default administrator passwords in source code.
29. Factories
Model factories should be used primarily for automated tests and development data.
Primary location:
database/factories/
Tests should use factories where they make setup clearer and more maintainable.
30. Database Transactions
Use transactions when multiple related database changes form one logical operation.
Example:
Create a record
→ create related records
→ assign relationships
If one required operation fails, the complete logical operation should roll back where appropriate.
Avoid wrapping simple independent single-row updates in transactions without need.
31. Mass Assignment
Models must explicitly control writable attributes.
Do not persist arbitrary request data using patterns such as:
Model::create($request->all())
Prefer validated data.
Examples:
$request->validated()
or explicitly selected values.
The implementation must protect internal fields from unintended assignment.
32. Enums
Enums may be used when a field has a stable, meaningful set of application states.
Recommended location:
app/Enums/
Potential examples:
- publication status
- content type
- workflow state
Do not create enums for every small list when configuration or database data is more appropriate.
33. Value Objects
Value Objects may be used when they provide clear domain value.
Recommended location if needed:
app/ValueObjects/
Do not introduce them as a mandatory architectural pattern.
Use them only when they improve correctness, clarity, or validation for meaningful concepts.
34. Helpers
Global helper functions should be used sparingly.
Do not create large generic helper files.
Prefer:
- framework functionality
- focused classes
- Blade components
- model methods
- Actions
- Services
when they provide clearer ownership.
If a helper is genuinely useful and broadly reusable, keep it small and well-defined.
35. Traits
Traits should be used carefully.
Do not use traits to hide large amounts of unrelated behavior.
Use them only for small, coherent behavior shared across suitable classes.
Inheritance or composition may be preferable depending on the requirement.
36. Configuration
Application configuration belongs under:
config/
CMS-specific application configuration may use:
config/cms.php
Configuration files should read environment-specific values using Laravel configuration conventions.
Application code should normally read values through:
config(...)
rather than calling env(...) outside configuration files.
37. Environment Variables
Environment variables belong in:
.env
Safe examples belong in:
.env.example
Do not place business configuration that administrators should edit at runtime into .env merely for convenience.
Runtime website settings should eventually be managed through the CMS settings module where appropriate.
38. File Storage
Use Laravel's filesystem abstraction.
Do not directly hard-code operating-system storage paths for application media.
Use configured disks where appropriate.
Current development may use local storage.
Production storage architecture is not yet selected.
39. Media Architecture
The Media Library will eventually own media-management behavior.
Other features should reference managed media rather than independently inventing separate upload systems where practical.
Exact media architecture must be defined by the Media Library feature.
Do not prematurely implement a global media abstraction before that feature is approved.
40. SEO Architecture
SEO concerns should remain separable from business content where practical.
Content entities may expose SEO-related fields or relationships once defined by the approved SEO architecture.
Do not duplicate SEO implementation independently inside every feature.
The SEO feature will define the common strategy.
41. Theme Architecture
CMS core functionality must remain separate from theme presentation.
Themes may determine:
- frontend layout
- visual components
- content presentation
- branding
- page templates
Themes must not own:
- authentication logic
- authorization logic
- user permissions
- CMS core persistence rules
Theme architecture will be defined in its approved feature.
42. External Integrations
External service integrations should use clear boundaries.
If an approved feature introduces an external provider, consider an interface or service abstraction when it provides practical value.
Examples may include:
- email delivery provider
- storage provider
- AI provider
- payment provider
Do not create abstractions for integrations that do not exist.
43. Events and Listeners
Laravel events/listeners may be used when multiple independent reactions need to occur after a meaningful application event.
Do not use events merely to avoid direct method calls.
Avoid making simple workflows difficult to trace.
If only one direct operation is required, direct invocation may be clearer.
44. Jobs and Queues
Jobs may be used when work is:
- expensive
- asynchronous
- retryable
- unsuitable for the request-response cycle
Queue infrastructure has not yet been approved.
Do not introduce queued architecture until an approved feature requires it.
45. Notifications
Use Laravel notification facilities where they fit approved requirements.
Do not create email/SMS/push infrastructure before a feature requires it.
Production providers must be separately approved/configured.
46. API Development
Do not create an API layer for functionality that only needs Blade-based web access.
If an approved feature requires an API:
- define its consumers
- define authentication
- define authorization
- define versioning if required
- define response contracts
- add appropriate tests
Do not create APIs “for future use.”
47. Error Handling
Do not silently swallow exceptions.
Unexpected application failures should be handled using Laravel's exception and logging infrastructure.
Users should receive safe messages.
Detailed exception information must not be intentionally exposed in production-facing responses.
Avoid broad patterns such as:
catch (\Exception $e) {}
without meaningful handling.
48. Logging
Log meaningful operational or unexpected application failures.
Do not log:
- passwords
- API keys
- access tokens
- private keys
- full sensitive request payloads
Avoid excessive logging that creates noise or unnecessary storage usage.
Activity auditing and technical logs are separate concerns.
49. Security Boundaries
Security must be enforced in backend application logic.
Do not rely on:
- hidden buttons
- disabled fields
- client-side checks
- URL secrecy
Every sensitive operation must validate both:
- whether the request is valid
- whether the current user is authorized
Detailed security requirements are maintained in:
docs/06_SECURITY_RULES.md
50. CSRF
Standard Laravel web forms must retain CSRF protection.
Do not disable CSRF middleware to fix form issues.
Fix the underlying implementation instead.
51. Output Escaping
Use normal Blade escaping:
{{ ... }}
for untrusted content.
Use unescaped rendering only when the application explicitly knows content is safe or has been sanitized appropriately.
Do not render user-managed HTML as raw HTML without considering XSS risk.
52. Testing Architecture
Feature tests are the preferred test type for HTTP/application behavior.
Use Unit tests for isolated business logic where appropriate.
Tests should cover behavior rather than internal implementation details whenever reasonable.
Testing rules are defined in:
docs/04_TESTING_STRATEGY.md
53. Testability
Architecture should allow important behavior to be tested without excessive setup.
Avoid:
- static global state
- hidden external calls
- hard-coded dependencies
- logic buried entirely in Blade templates
Use dependency injection where it improves testability and design.
54. Naming
Use meaningful Laravel-style naming.
Examples:
Controller:
PageController
Form Request:
StorePageRequest
Action:
PublishPage
Policy:
PagePolicy
Model:
Page
Migration:
create_pages_table
Avoid vague names such as:
Manager
Processor
Handler
Helper
unless the name clearly describes a specific responsibility.
55. Class Responsibility
Each class should have a clear purpose.
If a class begins handling multiple unrelated responsibilities, consider separating them.
Do not interpret this as a requirement to create many tiny classes.
Balance cohesion with simplicity.
56. Dependency Direction
Presentation concerns should depend on application/domain behavior rather than application behavior depending on Blade views.
Database models should not depend on controllers.
Services should not depend on Blade templates.
Authorization should not be implemented through UI visibility alone.
Keep dependencies flowing toward reusable application logic where practical.
57. Avoid Circular Architecture
Do not create circular dependencies such as:
Service A depends on Service B
while:
Service B depends on Service A
If such a dependency appears necessary, reconsider responsibilities.
58. Package Code
Do not modify files under:
vendor/
Do not directly modify installed npm package code under:
node_modules/
Package behavior should be customized using supported extension mechanisms.
59. Generated Files
Do not manually edit generated build outputs unless the toolchain explicitly requires it.
Examples include:
public/build/
Dependencies and build processes should generate these files.
Source changes belong under the relevant source directories.
60. Directory Creation
Do not create all theoretically possible directories in advance.
Create directories when actual implementation requires them.
Potential directories such as:
app/Actions/
app/Services/
app/Policies/
should contain real functionality rather than existing solely to satisfy an architecture diagram.
61. Current Application Structure
The project currently uses or plans to use structures similar to:
app/Http/Controllers/
app/Http/Requests/
app/Models/
app/View/Components/
resources/views/admin/
resources/views/frontend/
resources/views/components/
routes/admin.php
routes/frontend.php
database/migrations/
database/factories/
database/seeders/
Additional directories should be created only when required.
62. Authentication Architecture
Laravel Breeze provides the authentication foundation.
Do not replace Breeze with another authentication system without explicit architectural approval.
Authentication UI may be integrated into the CMS layout.
Authentication backend behavior should remain compatible with standard Laravel conventions unless an approved requirement changes it.
63. RBAC Architecture
Role-based access control is planned but not yet fully defined by this architecture document.
The RBAC feature will define:
- package approval
- roles
- permissions
- middleware
- policies
- Super Admin behavior
- initial administrative user provisioning
Do not invent RBAC behavior in unrelated features.
64. Super Admin
A Super Admin concept is planned.
Do not assume Super Admin automatically bypasses all authorization checks until the RBAC feature explicitly defines that behavior.
Security-sensitive bypass behavior requires explicit design and tests.
65. Public Registration
Public registration is temporary during early authentication development.
The RBAC/admin provisioning feature should define its final behavior.
Do not treat public CMS registration as a permanent product requirement.
66. Admin Architecture
Administrative functionality should use a consistent structure.
Potential modules include:
- Dashboard
- Users
- Roles
- Permissions
- Settings
- Media
- Pages
- Menus
- SEO
- Services
- Projects
- Blog
- Testimonials
- Clients
- Gallery
- FAQs
- Contact Messages
- Activity Logs
Each module should follow consistent routing, authorization, validation, view, and testing conventions.
Do not implement these modules until their features are approved.
67. Frontend Architecture
The frontend consumes CMS-managed content.
Frontend templates should focus on presentation.
Avoid embedding administration-specific logic in public frontend views.
The Dewatering India frontend should eventually become one implementation/theme on top of reusable CMS capabilities.
68. Architectural Decision Records
Significant architecture decisions should be documented using ADRs under:
docs/decisions/
Use an ADR when a decision:
- meaningfully changes architecture
- introduces a major dependency
- creates long-term constraints
- selects between important alternatives
- affects multiple future features
Do not create ADRs for ordinary implementation details.
69. Architecture Change Approval
Before changing this architecture materially:
1. Identify the limitation in the current architecture.
2. Explain the proposed change.
3. Explain alternatives considered.
4. Explain benefits.
5. Explain risks.
6. Explain migration impact.
7. Explain testing impact.
8. Explain maintenance impact.
9. Request explicit user approval.
If appropriate, prepare an ADR.
Do not implement the architectural change before approval.
70. Architecture and Budget
Architecture work must follow the project's low-budget AI policy.
Do not spend tokens:
- redesigning working architecture without need
- comparing many theoretical architectural patterns
- producing extensive diagrams for simple features
- repeatedly reviewing unchanged architecture documents
- introducing abstractions for possible future scenarios
For normal features:
use the existing architecture unless a concrete requirement demonstrates that it is insufficient.
71. Architecture Decision Rule
When deciding where code belongs, use this sequence:
1. Can standard Laravel functionality solve it clearly?
2. Does the logic belong naturally in the model?
3. Is it request validation?
4. Is it authorization?
5. Is it one focused application operation suitable for an Action?
6. Is it a reusable business/integration capability suitable for a Service?
7. Is a new abstraction genuinely necessary?
Choose the simplest option that maintains clear responsibility and testability.
72. Final Architecture Principle
The architecture should make the CMS easier to understand, not harder.
If an abstraction adds more files, indirection, configuration, and cognitive load without solving a concrete problem, do not introduce it.
Prefer:
simple
clear
secure
testable
Laravel-native
incrementally extensible
over:
abstract
speculative
complex
framework-within-a-framework
The user remains the final authority for major architectural decisions.
